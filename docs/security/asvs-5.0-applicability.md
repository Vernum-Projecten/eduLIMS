# ASVS 5.0 applicability

This table holds every requirement of the OWASP Application Security
Verification Standard 5.0.0 against eduLIMS: whether it applies, where the
code meets it or will meet it, how that is verified, and its status today.
The requirement text is in the vendored chapters
([vendor/asvs/en/](vendor/asvs/en/)); look one up by id with `/owasp-lookup`
or `grep -n 'V6.8.1' docs/security/vendor/asvs/en/*.md`.

## Target: ASVS Level 2

eduLIMS targets **ASVS Level 2**. It holds personal data of students
(names, student numbers, e-mail addresses, grades and lab results) under the
GDPR, it serves three roles whose data must stay apart (R-01, the highest
risk in the requirements, and Q-SEC-2), and it is reachable from the
institution's network with single sign-on. Level 1 is the floor for any
application and does not cover the access control, session and logging depth
this needs; Level 3 is meant for systems whose compromise causes serious harm
(medical devices, finance, critical infrastructure), and the measurements here
are teaching material, not patient data. A Level 3 requirement appears in the
table as not applicable unless eduLIMS meets it anyway.

## How to read the table

- **L:** the ASVS level of the requirement (1, 2 or 3), from the vendored list.
- **Applies:** `yes`, `partly` (part of it is the identity provider's or the
  operator's), or `no` with the reason in **Where**.
- **Where:** the file, ADR, issue or requirement ID that meets it or will
  meet it. "The operator" means the deployment outside this repository (the
  reverse proxy, the host), described in `docs/deployment.md`.
- **Verification:** the unit, e2e or integration test, the CI job, review,
  or a manual check that proves it. "Review" means no automated check proves
  it yet; a reviewer reads the code.
- **Status:**
  - `met`: the code does it today, at the cited file or test.
  - `partial`: some of it is done; the rest is named in **Where**.
  - `planned`: no code yet, and an issue or a draft requirement (S, D, B or
    Q ID) carries the work.
  - `open`: no code and no issue yet; a gap to file and decide.
  - `n-a`: does not apply (status of every `no` row).

Requirement IDs (S4, D3, B4, Q-SEC-2) are from the draft in
[docs/requirements.md](../requirements.md) and can change; the owner's
decision on an issue is newer than the draft.

## Updating

The rows come from the vendored machine-readable list
(`vendor/asvs/docs_en/OWASP_Application_Security_Verification_Standard_5.0.0_en.flat.json`).
`node scripts/security/asvs-table.ts` rewrites the region below, keeping every
hand-written cell, adding a row with `TODO` cells for a new id, dropping a
row whose id is gone, and recounting the summary. `bash
scripts/checks/asvs-coverage.sh` (the `asvs-coverage` CI job) fails when an
id is missing, unknown, duplicated or still `TODO`, or when **Applies** and
**Status** disagree. Change a cell by hand when the code changes: a new test
moves a row to `met` in the same pull request.
