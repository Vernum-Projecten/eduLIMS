# 0017. Provisioning users with SCIM 2.0

- Status: Proposed
- Date: 2026-11-11
- Deciders: maintainer (on the owner's delegation, #32 and #45)
- Amends: [0015](0015-runtime-identity-providers.md) (the sso plugin's
  `resolveUser` now links a sign-in, on the directory id only)

## Context and problem statement

Users appear in eduLIMS at their first sign-in, so an administrator cannot
see a class before the students sign in, and a person who leaves keeps their
access until their eduLIMS session expires and the identity provider refuses
the next sign-in. Identity providers (Microsoft Entra ID, Keycloak through an
extension) push users and groups over SCIM 2.0 (RFC 7643, RFC 7644). How does
eduLIMS take that push without weakening sign-in, the role model (ADR 0012,
hybrid ownership on #32) or account isolation between providers (#39)?

## Considered options

1. **No SCIM;** administrators create users by hand.
2. **`@better-auth/scim` with its managed connection catalog** (connections
   and HMAC-digested credentials the plugin stores, with expiry).
3. **`@better-auth/scim` with an eduLIMS token table** verified through the
   plugin's `authentication.verifyBearerToken`, one connection per identity
   provider.
4. **A SCIM endpoint written in eduLIMS.**

## Decision

Option 3, with `@better-auth/scim` at exactly 1.7.20 like `better-auth` and
`@better-auth/sso`.

- **One connection per identity provider.** The SCIM connection id and
  provisioning domain are the provider id, so every SCIM resource is scoped
  to its provider and a token of one provider never reads or changes another
  provider's users (the plugin answers 404).
- **Tokens:** `edulims_scim_` plus 256 random bits, generated by eduLIMS,
  shown once, stored as a SHA-256 digest in `scim_token` (one current token
  per provider, a partial unique index). A token expires after 180 days; the
  provider's page shows the date and warns from 14 days before, and an
  expired token is refused and logged (`scim_token_refused`,
  `token_expired`). A rotation keeps the previous token for one hour, never
  past its own expiry, so the identity provider switches without a gap; a
  revocation ends every token of the provider at once (owner decision on
  #45). Create, rotate and revoke run from the provider's detail page and
  the host CLI (`scim token create|rotate|revoke`, which prints the expiry),
  through one service that writes the activity log in the same transaction.
  A token of a disabled provider is refused. The managed catalog of option 2 was not taken: it needs a second
  long-lived secret (`credentialHashSecret`), its connection ids are not the
  provider id, and it has no per-provider enabled switch.
- **Identity on the directory `externalId`, never email.** A new SCIM user
  links to an existing eduLIMS user only when that user has an account at the
  same provider whose account key equals the `externalId`; otherwise SCIM
  creates the user. At sign-in, the sso plugin's `resolveUser` reads the
  directory id (the account key, or the claim or SAML attribute the provider
  names in `scim_external_id_claim`) and calls the plugin's
  `acquireActiveSCIMUserLink` for that provider's connection: an active SCIM
  user is linked, one the directory deactivated or deleted is refused with
  `account_deprovisioned`, and anyone else signs in as before. Account
  linking by email stays off (#39). Only an immutable claim may carry the
  directory id: `oid`, `sub`, `objectGUID`, or the account key (the OIDC
  `sub`, the SAML persistent NameID); `email` or `preferred_username` is
  refused. Each sign-in stores its directory id on the account
  (`account.directory_id`), so a later SCIM create links that user instead of
  making a second one. Whoever controls the directory's `externalId` mapping
  controls the linking.
- **One owner per e-mail address** (H1, V6.8.1): a SCIM create or change
  whose address belongs to a user another sign-in method owns (an account at
  another provider, a user another provider provisioned, a local user) is
  refused before the plugin runs, with a generic 409 `uniqueness` that names
  no user and no provider, and a refused row in the activity log. That a
  directory learns an address is taken is an accepted risk: every SCIM
  client is an institution's directory an administrator configured.
- **E-mail domains** (owner decision on #45): when a provider has e-mail
  domains, a SCIM create or change that sets an address outside them is
  refused with a generic 400 `invalidValue` and a refused row
  (`address_domain`), so a directory cannot claim an unused address of
  another institution. A provider without domains is unrestricted, and its
  page warns about that.
- **Roles follow hybrid ownership (#32).** The plugin's role projection maps
  a SCIM group on its `externalId` alone (a group without one maps no role;
  a display name can be renamed by any directory administrator) and the
  user's `roles` values through the provider's own role map. A mapped set is
  authoritative with the provider as `role_source`; a conflicting set leaves
  no roles; a set the provider took away is removed and the sessions end
  (A07); a local set stays. A user SCIM creates has no roles (the admin
  plugin's default role is not applied), and the provider's default role does
  not apply at that user's sign-in. SCIM gives no role the map does not name,
  so it never gives admin unless the map maps a group to it.
- **SCIM owns the roles of its users** (security review B1, ASVS V8.2.1, and
  the owner's decisions on the second and third reviews): for a user any
  provider provisioned (`provisioned_by` set), the claims of a sign-in
  through any provider never change the roles, neither adding nor removing
  one, so another provider's claim can never add admin; a SCIM write sets them from the role map, taking away
  any set that provider gave, a claim's from before the link included; only
  local roles an administrator gave stay. For a user SCIM did not provision,
  the claim rules of ADR 0015 hold, so a set a claim gave, admin included,
  is gone at the next sign-in without that claim. `user.role_channel`
  (`claim`, `scim`, `local`, backfilled to `claim` for existing provider
  sets) records which writer set the roles. Neither channel can flip the
  other's set back and forth.
- **Deactivation:** `active: false` or a delete marks the user
  `deprovisioned_at`, ends every session in the plugin's transaction, and a
  `databaseHooks.session` hook refuses every new session. Records stay;
  erasure is #47. Reactivation clears the mark.
- **Prerequisites, checked:** the plugin and `resolveUser` need native
  interactive transactions, database sessions and better-auth's async
  context. `createAuth` checks the first two before it adds the plugins, a
  guard plugin checks the third at the first SCIM request, and without them
  `/api/auth/scim/v2` answers 501 (`src/server/scim/support.test.ts`).
- **Guards:** a fixed-window rate limit of 600 requests per minute, in two
  tables: one per provider for a working token, never evicted by client
  keys, and one per client IP for every other request, bounded and answering
  429 when full. The token is looked up first (one indexed digest lookup
  per request), so a working token counts only against its provider and a
  directory on shared egress addresses, such as Entra ID's, is never held up
  by others' bad tokens; deprovisioning must not stall (V7.4.2). The client IP comes from `X-Forwarded-For` only through the
  proxies in `EDULIMS_TRUSTED_PROXIES` (better-auth's `advanced.ipAddress`,
  the chain walked right to left); without them every client shares one
  bucket, so a spoofed header buys nothing. A 1 MiB body cap. An
  activity-log row for every SCIM write and every refused read or write
  (403, or 404 for another provider's resource); a refused token is
  `scim_token_refused` with why, an unknown or missing one once per client
  and minute with the count it stands for, any other once per token and
  minute. Ids and codes only. The plugin's server-only endpoints
  (decommission, reconcile) are not reachable over HTTP.

## Consequences

- An administrator sees provisioned users ("Provisioned by …", "Never signed
  in") before their first sign-in, and the directory ends access at once.
- A SCIM token is a bearer credential that lives 180 days (ASVS V13.2.1 asks
  for short-term tokens). It is hashed, expires, rotates with a one-hour
  overlap, is revocable at once and is bound to one provider; the identity
  providers' SCIM clients take a static secret, so a shorter life would mean
  more manual rotations.
- `resolveUser` runs on every SSO sign-in inside the account transaction.
- The rate limit lives in process memory: a restart resets it, and several
  app replicas would each count their own.
- A provider that provisioned users cannot be deleted
  (`has_provisioned_users`), as one with accounts cannot: the plugin's tables
  have no foreign key to `identity_provider`, so a deletion would orphan
  them.
