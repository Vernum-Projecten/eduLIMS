# Database: PostgreSQL 18 with Kysely

The eduLIMS database holds the simulation: users, roles and classes; games
and teams with their lab names; the test catalogue; correct values;
tolerances; patients, requests and samples with their lab numbers; the times
of entry and release; the upload log and the audit log
([lims-workflow.md](../../docs/lims-workflow.md#who-owns-what-and-where-it-lives)).
Results live in FerroEHR as compositions (`integration.md`); where a
measurement lives before its release is a design matter, with the
maintainer's proposal in `docs/lims-workflow.md`.
A request is for one patient or for a control sample, which has no patient
(S16). The correct values are keyed by game, sample number and test, never
by team (D10).
A request has no urgent flag and no time target in this iteration (D12, O1),
and nothing stores a ranking (D14, O3).
Both databases run on one PostgreSQL 18 server, each with its own database
user: the eduLIMS app user never has rights on the FerroEHR database.

## Kysely

- **Kysely** is the query builder (<https://kysely.dev/docs/intro>): typed
  SQL, no ORM, no runtime model layer. The `Database` interface is
  **generated** from the live schema by `pnpm db:generate-types` (kysely-codegen)
  and never edited by hand; regenerate it in the same change as the migration
  that alters the schema (`/db-migration`).
- **Bound parameters only.** Build queries with the query builder or the
  `sql` template tag, whose `${value}` is a parameter. `sql.raw` and
  `sql.lit` take no request-derived value, ever (OWASP A05).
- **The ownership filter is part of the query** (`auth-security.md`): a
  teacher's query joins on the game's teacher, a student's query joins on the
  team of the student id from the session, in SQL. Never select broadly and filter in
  TypeScript.
- **Select the columns the screen needs**, never `selectAll()` on a table with
  personal data or correct values, so a new column does not leak through an
  old endpoint. Only a teacher-scoped query selects a correct value, the
  teacher's limits or anything computed from them (Q-SIM-1, D10).
- **Transactions** (`db.transaction().execute(…)`) for every change that
  touches more than one row that must agree: recording a request writes the request, its
  tests, its samples and its time of entry together (S12); releasing a result
  writes the result and its time of release together (S15).
- Queries live in `src/server/<area>/` next to the server functions that use
  them; the `db` instance and the connection pool are created once in
  `src/server/db/` and imported, never constructed per request.

## Schema rules

- **Keys:** `uuid` primary keys generated by PostgreSQL 18's `uuidv7()`
  (<https://www.postgresql.org/docs/18/functions-uuid.html>), so ids sort by
  creation time and do not reveal a count. The sample number is a
  separate column that the team types from the request form (S12). It is
  never a key on its own: every team works the same sample numbers, so a
  sample is identified within its team (R-11).
- **The test catalogue is data** (D9): a test is a row with its name, unit
  and material, never an enum or a constant in code.
- **Time:** `timestamptz` for every instant (the entry of a request, the
  release of a result), set by the database or the server inside the
  transaction, never taken from the request (Q-SIM-2); never `timestamp`
  without time zone.
- **Constraints carry the rules the database can hold:** `NOT NULL`,
  `CHECK` (a tolerance's lower limit not above its upper limit), foreign
  keys with an explicit `ON DELETE`, at most one released result per
  requested test (a released result is final, S15), a lab number that is
  unique across the teams of every game (S12), and enums or `CHECK ... IN` for statuses (the states of a
  requested test in `docs/lims-workflow.md`). The application validates too,
  but the database is the last line.
- **Names:** `snake_case`, plural table names, `<table>_id` foreign keys.
  The better-auth tables (`user`, `session`, `account`, `verification`) are
  singular, and `audit_event` sits beside them with the same form.
- **The activity log** (`audit_event`, B4) holds ids and codes only and is
  written through `recordAudit` (`src/server/audit/record.ts`), inside the
  transaction of the action it records. The app server applies the retention
  periods (12 months for events, 30 days for expired sessions) every 24 hours
  through `runPrune` (`src/server/audit/prune-job.ts`); `pnpm db:prune` runs
  the same code by hand.
- **No real person in FerroEHR, and the link to the team lives here:**
  FerroEHR holds the fictional patients of a game and no student or teacher
  (Q-PRIV-1). Which team and which game a patient, a request and a result
  belong to is recorded only in the eduLIMS database, and only server code
  with a reason reads it.

## Migrations

- One migration per schema change, in `src/server/db/migrations/`, named
  `<NNNN>_<snake_slug>.ts` (the next free four-digit number, registered in
  `migrations/index.ts`) and exporting `up` and `down`
  (<https://kysely.dev/docs/migrations>). Write the SQL with Kysely's schema
  builder, or `sql` for a PostgreSQL feature it lacks.
- **Before 1.0 (greenfield):** there is no production data, so a migration
  may be edited, renumbered or merged into another; local databases are
  reset with `pnpm db:reset`, and no change needs a data migration or a
  compatibility path ([[greenfield-until-1-0]] in `.claude/memory/`). Parallel
  branches still take distinct numbers so they merge cleanly.
- **From 1.0 on:** the migrations are squashed into one baseline at the 1.0
  cut, and from then a merged migration is immutable: a mistake is fixed by
  a new migration, never by editing, renaming or reordering one on `main`.
- `down` really reverts `up`; a destructive `down` (dropping a column with
  data) says so in a `// NOTE:`.
- Run with `pnpm db:migrate` against the Compose database (`pnpm dev:db`);
  `pnpm db:reset` empties the local development database and migrates and
  seeds it again. The test run and CI run the migrations from empty every
  time, so a migration that only works on your local data fails there.
- Data migrations that rewrite rows are separate from schema migrations and
  are idempotent.

## Test data

Seeds and fixtures use the fixed pseudonymised test set only (`testing.md`):
invented students in invented teams, one game with invented patients,
requests and correct values, and HbA1c, CRP and absorbance values. Never
import a real class list, and never copy a patient, a request form or a
correct value from the teachers' game material (Q-PRIV-4).
