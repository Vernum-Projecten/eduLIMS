# Database: PostgreSQL 18 with Kysely

The eduLIMS database holds everything except measurements: users, roles and
classes; practicals (assignment, protocol, rubric, deadline); sample IDs with
their link to student and practical; lab reports; assessments, grades and
feedback; the upload log and the audit log
([architecture.md](../../docs/architecture.md#data)). Measurements live in FerroEHR (`integration.md`).
Both databases run on one PostgreSQL 18 server, each with its own database
user: the eduLIMS app user never has rights on the FerroEHR database.

## Kysely

- **Kysely** is the query builder (<https://kysely.dev/docs/intro>): typed
  SQL, no ORM, no runtime model layer. The `Database` interface is
  **generated** from the live schema by `pnpm db:generate-types` (kysely-codegen)
  and never edited by hand; regenerate it in the same change as the migration
  that alters the schema (`/db-migration`).
- **Bound parameters only.** Build queries with the query builder or the
  `sql` template tag, whose `${value}` is a parameter. `sql.raw` and
  `sql.lit` take no request-derived value, ever (OWASP A05).
- **The ownership filter is part of the query** (`auth-security.md`): a
  teacher's query joins on the practical owner, a student's query filters on
  the student id from the session, in SQL. Never select broadly and filter in
  TypeScript.
- **Select the columns the screen needs**, never `selectAll()` on a table with
  personal data, so a new column does not leak through an old endpoint.
- **Transactions** (`db.transaction().execute(…)`) for every change that
  touches more than one row that must agree: submitting a lab report sets the
  status and the timestamp together (S6); finalising an assessment writes
  every rubric score and the computed grade together (D4).
- Queries live in `src/server/<area>/` next to the server functions that use
  them; the `db` instance and the connection pool are created once in
  `src/server/db/` and imported, never constructed per request.

## Schema rules

- **Keys:** `uuid` primary keys generated by PostgreSQL 18's `uuidv7()`
  (<https://www.postgresql.org/docs/18/functions-uuid.html>), so ids sort by
  creation time and do not reveal a count. The human-readable sample ID
  that a student types on the Afinion 2 and puts in the Gen5 export is a
  separate column with a `UNIQUE` constraint (S3: "with 50 registered samples,
  all 50 sample IDs are unique"), generated by the
  server, never by the client.
- **Time:** `timestamptz` for every instant (submitted at, deadline, assessed
  at); never `timestamp` without time zone.
- **Constraints carry the rules the database can hold:** `NOT NULL`,
  `CHECK` (a rubric score within its range, a grade between 1 and 10), foreign
  keys with an explicit `ON DELETE`, and enums or `CHECK ... IN` for statuses
  (`concept`, `ingediend`, `beoordeeld`, S8). The application validates too,
  but the database is the last line.
- **Names:** `snake_case`, plural table names, `<table>_id` foreign keys.
- **No personal data in FerroEHR, and the pseudonym map lives here:** the
  table that maps a student to their EHR pseudonym is the only place the two
  meet, and only server code with a reason reads it.

## Migrations

- One migration per schema change, in `src/server/db/migrations/`, named
  `<UTC timestamp>_<snake_slug>.ts` and exporting `up` and `down`
  (<https://kysely.dev/docs/migrations>). Write the SQL with Kysely's schema
  builder, or `sql` for a PostgreSQL feature it lacks.
- **A merged migration is immutable.** A mistake is fixed by a new
  migration. Never edit, rename or reorder one that has reached `main`.
- `down` really reverts `up`; a destructive `down` (dropping a column with
  data) says so in a `// NOTE:`.
- Run with `pnpm db:migrate` against the Compose database (`pnpm dev:db`);
  `pnpm db:reset` empties the local development database and migrates and
  seeds it again. The test run and CI run the migrations from empty every
  time, so a migration that only works on your local data fails there.
- Data migrations that rewrite rows are separate from schema migrations and
  are idempotent.

## Test data

Seeds and fixtures use the fixed pseudonymised test set only (`testing.md`):
invented students, one practical with a deadline and a rubric, and HbA1c, CRP
and absorbance values. Never import a real class list.
